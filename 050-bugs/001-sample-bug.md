## Reported behavior

Describe the observed behavior in one sentence. State what was actually seen,
not a theory about its cause.

## Expected behavior

Describe the contract or user-visible result that should have occurred. Link
the relevant design, runbook, or test when one exists.

## Reproduction evidence

Record enough detail for another operator to reproduce the issue safely:

```text
Machine and account: <for example, Mac — tomasz.walczuk>
Source revision: <Git SHA>
Configuration or mailbox context: <safe identifier only>
Command or action: <copy-pasteable safe command>
Observed result: <safe error/output excerpt>
```

Keep private keys, certificates, token values, raw secret files, and sensitive
command output out of this record.

## Impact and scope

State who or what is affected, whether a workaround exists, and which routes,
mailboxes, profiles, or hosts are known to be unaffected. Do not infer that a
result on one host applies to another.

## Investigation

List evidence in time order. Separate facts from hypotheses and link commits,
tests, logs, or phase evidence where useful.

## Fix and verification

Record the correction commit, then name the required verification gate and its
result. A fix remains `FIXED — PENDING VERIFICATION` until the required gate
passes. After closure, update the row in
[the bug register](000-bug-register.md).

## Resolution

For this sample: no action is required. Replace this section with the final
root cause, correction, verification evidence, and closure date for a real
bug.
