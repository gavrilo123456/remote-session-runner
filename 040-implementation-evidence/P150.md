## P150 scope and decisions

P150 freezes a configuration-only registry API. It does not change runtime
routing, mailbox processing, deployment, or live host state; those changes
belong to P151--P155.

1. Version 1 remains fully valid and is adapted in memory to one `default`
   mailbox, one `mac-local` context, one `ubuntu-current` context, one
   `linux-host` remote profile, and one `linux-poc` direct endpoint profile.
   Existing installed configuration and files are not moved.
2. Version 2 uses named execution contexts, named remote host profiles,
   endpoint profiles bound to a remote profile, and named mailbox definitions.
   Registry identifiers use a bounded filesystem-safe name syntax.
3. Version 2 keeps the PoC boundaries: local is only
   `local/mac-workstation`; remote profiles use account `ubuntu`; a request
   cannot provide hostnames, accounts, endpoints, paths, or secret values.
4. A remote host may have a pinned queued-bridge route, a direct endpoint, or
   both. A bridge is required when a mailbox is permitted to select that
   remote profile; a direct endpoint, if configured, is bound to that profile.
   Secret and certificate references remain absolute, canonical paths under
   the Mac service-root `secrets/` directory.
5. Mailbox roots must be absolute, canonical, unique, non-overlapping paths
   under the Mac service root. The legacy root is allowed only for `default`;
   additional roots live under `mailboxes/<inbox-id>`.
6. Each execution context must match a configured environment policy. Each
   mailbox must contain a nonempty unique allow-list and a default context in
   that allow-list. Repository aliases are mailbox metadata only and may be
   shared across inboxes; the durable inbox identity distinguishes them.
7. Existing scalar `MacSettings`, `LinuxSettings`, and fixed secret-reference
   accessors remain available for old consumers. P151/P154 will consume the
   new registries; P150 must not select an arbitrary host or mailbox at
   runtime.
8. Version 2 Linux configuration remains one service profile per Ubuntu host.
   It keeps the fixed `ubuntu` account and owner-only local service paths while
   allowing that host's own remote target profile, bind address, and public
   mTLS endpoint. It does not accept Mac mailbox/route registries.

## Implementation and review

The implementation adds `version: 2` parsing while preserving `version: 1`
as the installed configuration contract. It exposes immutable named execution
contexts, remote profiles, direct endpoint profiles, and mailbox definitions.
Version-one Mac configuration is synthesized in memory as the legacy
`default` mailbox and current `linux-host`; no installed files or mailbox
roots moved.

The v2 validation rejects unsafe credential reference paths, non-HTTPS or
non-8443 direct endpoints, endpoint user information, duplicate endpoint
names or context pairs, invalid mailbox defaults and allow-lists, profiles
without a permitted route, incorrect fixed accounts, and Linux TLS below 1.3.
It accepts a direct-only profile for CLI use when no mailbox can select it and
a queued-only profile for mailbox use. A remote profile selected by a mailbox
must have its pinned bridge.

The implementation was independently reviewed after the focused tests. The
review found and the final change corrected three issues before the phase gate:
v2 Linux must require TLS 1.3, environment effective accounts must match
their local/remote execution target, and v2 invalid runtime adapters must keep
the established safe error classification. No remaining source or test blocker
was found.
