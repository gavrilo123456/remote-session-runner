# P112 — Direct HTTPS mutation-wide idempotency matrix

## Phase contract

Run the direct HTTPS mutation-wide idempotency matrix under mapped controller identities. The gate is: create, submit, cancel, close, and run replay the same retained key and payload; changed behavior under that key conflicts; retries create no second resource or execution; and one controller cannot observe or mutate another controller's resources.

P112 is a hermetic loopback HTTPS/mTLS test gate. The public endpoint, firewall/source policy, and public client-certificate qualification belong to P117. The earlier temporary TLS route probe is transport evidence only and is not a Runner application test.

## Existing implementation and coverage review

The direct HTTPS handlers in `src/internal/runnerd/direct_api.go` derive controller identity only from the mapped direct principal in request context. Create, run, and submit canonicalize behavior-changing request fields before hashing. Submit includes session ID and effective timeout; cancel includes command ID; close includes session ID and normalized close policy. The store keys retained bindings by controller, operation, and idempotency key. Service ownership checks occur before mutation, and replay/conflict decisions are persisted before runtime work.

Existing P107–P110 tests already cover:

- Create: equivalent JSON ordering/defaults replay the original session; no second session or capacity reservation.
- Submit: same-key replay returns the original command; changed script and reuse on another session conflict; runtime starts once.
- Cancel: same-key replay returns the original command; a different controller is denied.
- Close: same-key replay returns the original session; changed close policy conflicts.
- Run: same-key replay returns stable job/session/command IDs; changed script conflicts; runtime command and teardown each occur once.
- Loopback HTTPS tests map a client certificate to `direct_mtls:tomasz.walczuk` for create, lifecycle, submit, and run operations.

Gaps for P112 assertions:

- No cancel test reuses one controller's cancellation key against a different command and verifies conflict before the second command is affected.
- No close test reuses one controller's close key against a different session and verifies conflict before that session is affected.
- Existing replay/conflict tests mostly inject a principal into the handler; add one complete matrix through loopback HTTPS with certificate-mapped identities and verify a second mapped controller cannot read/mutate the first controller's resources or inherit its idempotency result.
- Extend create coverage to explicitly assert same-key changed behavior conflicts with no second session/reservation.
- Preserve assertions that replay never causes another execution or close side effect.

No production defect is established by inspection; P112 begins as a coverage phase. If the matrix exposes a behavior defect, record the failing case before changing implementation.
