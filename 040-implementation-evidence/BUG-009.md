## B009-P2 result

**Passed source phase.** Commit `22d44ce4e4492bf932afcf15dbcda304e09b7992`
(`phase(B009-P2): recover retained lost capacity on dispatcher ticks`) adds a
bounded automatic path only after the normal dispatcher tick gets
`ErrCommandSlotsFull`. It reads only the P1 exact retained-lost candidate set,
performs existing process-group proof and the queue-preserving paired release,
then wakes the same dispatcher to claim the already accepted queued command.
It neither reads/replays a lost script nor creates a replacement request,
job, session, command, or scheduler.

The paired release now writes a durable pending-finalization row in the same
SQLite transaction. The row pins its command/session metadata until the owned
workspace/marker finalization succeeds. Startup finalizes those rows before
ownership audit; a failure blocks that startup safely. Dispatcher retries for
post-release finalization and retained-capacity proof use independent bounded
throttles, so a marker-cleanup failure cannot prevent later capacity recovery.
Migration `0032` intentionally does not reinterpret historical released-lost
rows that used the older reconciliation protocol.

## B009-P3 result

**Passed source phase.** Commit `259a808d418d009e262a6aa46afe5ec6e79050e0`
(`phase(B009-P3): expose retained capacity queue status`) adds the one allowed
optional fixed value, `queue_blocked_reason: lost_capacity_recovery_pending`.
The Linux authoritative job read computes it in the same read transaction as
the returned job state, only after controller authorization and only when the
exact P2 retained-lost-capacity inventory contains the matching safe queued
one-off reservation. The normal durable job record remains free of this
volatile status.

The field flows through the private/direct Linux job response, the selected
SSH bridge parser, the Mac remote projection, and the matching active mailbox
`run` response. It is accepted only in the exact nonterminal shape
`awaiting_command` / `queued`; unknown values or a running/terminal state are
rejected. The response revision changes when the field appears or disappears.
An unreadable remote status retracts it and records only the existing sanitized
status failure state; a fresh `running` status clears both the failure marker
and the blocked reason. The terminal-proof-only local Unix job-read boundary
remains unchanged, so P3 does not weaken P149's protection against presenting
an unproved remote result as local authority.
