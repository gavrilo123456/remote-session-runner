## P164 contract and planned gates

Migration 30 will add a mailbox-scoped, one-record-per-request-ID diagnostic
ledger. Its immutable core is a SHA-256 fingerprint of bounded raw request
bytes, a fixed diagnostic code, frozen sanitized diagnostic JSON and checksum,
revision, and observation time. It stores no raw request, script, operation,
idempotency key, target, parser error, credential, or header.

The separate lifecycle fields distinguish a crash replay from a later reuse of
the retained request ID: diagnostic projection, input-cleanup start and pair
removal, seven-day diagnostic-file cleanup, and final metadata cleanup at the
normal 90-day boundary. A changed fingerprint or a pair republished after
cleanup begins cannot overwrite the frozen diagnostic or become executable.

The focused automated gates are: fresh and v29 migration; same-fingerprint
replay; changed-fingerprint/request-ID reuse; frozen-core mutation rejection;
no raw request/idempotency/script persistence; and diagnostic artifact then
metadata lifecycle eligibility. The full P164 gate is focused store tests,
`make test`, `go test -race ./...`, `make vet`, `make build`, `make smoke`,
and `git diff --check` using the selected Mac Go 1.27.1 toolchain and shared
Go caches. No host test is applicable before P165 behavior and P166's harmless
direct-workspace acceptance.

## Implementation and automated gates

Migration 30 adds the separate `mailbox_ingress_diagnostics` ledger and its
cross-table identity guards. The frozen row contains only the trusted mailbox
and filename request identities, a SHA-256 fingerprint of bounded input,
fixed diagnostic code, frozen sanitized diagnostic bytes/checksum, and
lifecycle timestamps. It does not persist a request body, script, operation,
idempotency key, target, parser detail, header, token, or private key.

The lifecycle order is enforced by both SQLite and store validation:

1. record the rejected ingress;
2. project its private diagnostic;
3. begin then finish safely revalidated input-pair removal;
4. after seven days, claim/remove the private diagnostic; and
5. after normal metadata retention, remove the ledger row.

A stored diagnostic reserves its mailbox/request identity from normal mailbox
acceptance. Same bounded-input fingerprints reload the frozen record; changed
fingerprints and any republish after input removal remain retained-ID reuse.
Cleanup claims are restart-safe, and active, unclaimed records remain visible
to P165 recovery so a missing diagnostic artifact can be rebuilt before its
deadline. An expired or cleanup-claimed record cannot be resurrected.

The v1 private `diagnostic.schema.json` freezes the exact safe fields and five
code/message pairs. It is deliberately separate from the normal response,
event, and ACK contracts.
