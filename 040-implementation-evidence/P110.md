## Phase contract

- Phase: P110 — add direct HTTPS run/get-job using the shared one-off coordinator.
- Required focused gate: direct `I-04` subset; request bodies over 1 MiB and UTF-8 scripts over 128 KiB create no job; teardown failure remains visible in the job outcome.
- Keep the full dual-target PoC. Direct HTTPS runs remote targets only. The shared `ExecutionService.RunJob` coordinator owns the one-off workflow and durable outcome; do not implement a second executor in the HTTP handler.
- Direct routes are `POST /v1/jobs` and `GET /v1/jobs/{job_id}`. The mapped mTLS principal supplies controller identity; the request cannot override it. POST requires `Idempotency-Key` and explicitly names environment, remote target, and script. The direct handler allocates stable job/session/command IDs only after validating the request; the shared store preserves the original tuple on same-key/same-payload retry.
- The existing OpenAPI request body has a top-level `timeout_seconds` plus optional `limits`; the private run request represents command timeout under `limits.command_timeout_seconds`. P110 will normalize the top-level timeout into that shared limits field, reject invalid or conflicting values, and hash the resulting canonical run semantics.
- OpenAPI already describes JobAcceptance and JobReadResponse, but its POST job response list omits `413` even though direct input ceilings require rejection. P110 will document `413` for request/script oversize. Job acceptance returns stable IDs; GET provides command outcome/output and teardown state, including `lost` after unconfirmed teardown.
- P109's closeout is complete. This phase does not start or call the public Runner endpoint: P117 owns that gate. Existing temporary TLS probe evidence remains transport-only and is not a Runner application test.
- P143 physical power-cut testing remains a future gate. If either host cannot perform it, the software-crash-only durability claim still requires explicit user approval; none is assumed.

## Implementation and Mac gates

- Added direct HTTPS `POST /v1/jobs` and controller-scoped `GET /v1/jobs/{job_id}` over the existing shared `ExecutionService.RunJob` and `GetJob`. The direct caller cannot supply a controller or IDs; job/session/command IDs are allocated only after strict request, target, source, timeout/limits, script-size, canonicalization, and 1 MiB checks pass.
- Same-key/same-payload retries return the original stable job/session/command tuple; changed payload with the same key returns `409`. `timeout_seconds` maps to `limits.command_timeout_seconds`; conflicting values are rejected before ID allocation. The shared one-off coordinator remains the only execution path.
- Job reads use the OpenAPI `JobReadResponse`/`JobResource` fields and report phase, command state/exit code, output completeness, teardown state, mapped controller, remote target, and Ubuntu capabilities.
