# Pre-implementation decisions

**Status:** Pre-`P001` decisions selected and preflight evidence recorded; commit this note separately before `P001`. The three design/plan changes were committed in `a54bcdc`. This is the full planned dual-target PoC with one runtime change: the Linux executor runs directly as `ubuntu`, without Podman or a container. Actual Runner SSH/mTLS authorization, services, and runtime behavior must still pass their named later gates; the transport probe below is not an application test.

## Confirmed choices

- Source code belongs under `src/`, relative to the repository root. `go.mod` is at repository root; Go source packages and six command entrypoints go under `src/`, so root-level `go test ./...` and `go vet ./...` cover them.
- On the Mac, run the dispatcher/Router and local execution worker under the current macOS user: `tomasz.walczuk` (UID 501, home `/Users/tomasz.walczuk`). The source repository is `/Users/tomasz.walczuk/projects/remote-session-runner`.
- Local commands inherit the current user's macOS permissions. This is the selected account, not a separate Runner account or a Runner-specific filesystem permission layer. The initial design, detailed design, and plan now state this current-user model.
- Run `runnerd`, the SSH bridge, the remote session agent, Bash, and child commands directly as `ubuntu` (UID 1001, home `/home/ubuntu`) on `oracle-yuta-konopka-ubuntu-micro-02` (Ubuntu 20.04.6 LTS). Remote commands have `ubuntu`'s OS permissions; a workspace is a starting directory, not confinement. No Podman, container, sandbox, or per-command filesystem permission layer is part of this PoC.
- Keep the planned transports: versioned NDJSON over a pinned-host-key SSH forced-command bridge, and HTTPS with mandatory mTLS for direct remote access. For this PoC the direct endpoint is the host's public address `https://129.151.232.40:8443`; there is no SSH tunnel or bearer-token fallback. The server certificate must contain SAN `IP:129.151.232.40`, and only mapped client certificates authorize operations. This is Internet-facing PoC exposure, not a private-network deployment. A temporary mTLS probe has verified the network route; the Runner listener and application have not been built or tested.
- Select `10.0.0.200:8443` as `runnerd`'s Linux host-local HTTPS bind. `10.0.0.200` is the observed address on `ens3`; the public address is provider-mapped and is not a Linux interface address. A temporary TLS probe confirmed the public-to-local route, but no Runner listener is deployed yet.
- Select no source-IP allowlist for this PoC's public `8443` listener: a stable Mac egress IP and provider firewall control are not established, and a Mac-only allowlist would be brittle. The observed host INPUT policy is ACCEPT and the provider permitted the Mac probe, so regard `8443` as Internet-facing. Mandatory TLS 1.3 mTLS, explicit certificate-to-principal authorization, request/command ceilings, and negative security tests are required before enabling the real service. Source filtering may be added later as defense in depth; it is not a substitute for mTLS. This is a documented exposure decision, not a claim that the host is protected from arbitrary network traffic.
- Use the verified Go 1.27.1 toolchains installed under the respective service roots (paths below). The executables are not automatically on `PATH`; implementation commands and service definitions must use the absolute path or explicitly prepend their `bin` directory.

No real `git_revision` repository alias is enabled at kickoff. Implement and test the feature using explicit public/local test-fixture aliases in the planned source phases; do not silently treat an arbitrary repository URL as an approved alias. Adding a real repository alias later requires an explicit host-specific path/URL; a read-only credential reference is required only if that repository needs authentication. A credential owned by `ubuntu` is not OS-isolated from scripts also running as `ubuntu`; it must not be injected into the shell/workspace, but the PoC does not promise it is inaccessible. Direct HTTPS never accepts a local target. All incompatible target/profile, source, mount, and controller combinations reject before execution. Neither host profile advertises container isolation or unverified OS resource limits.

The design's **service-level ceilings** are the selected starting values: 20 active sessions and 4 running commands per host; 128 KiB script and 1 MiB serialized request; 30-minute command and idle timeouts; 4-hour session lifetime; 100 MiB command output; 1 MiB subscriber and 16 MiB persistence buffers; 90-day metadata/idempotency and 30-day output retention. These are Runner admission/output/time limits, **not** Linux CPU/memory/PID/disk/network confinement or Mac sandboxing. Requests requiring unavailable per-session OS controls reject rather than silently weaken. Real-host tests must measure effective capacity and account permissions.

Selected controller IDs are `(local_user, tomasz.walczuk)` for Mac Unix socket and mailbox, `(queued_mac, tomasz.walczuk)` for the dedicated bridge key as mapped **server-side**, and `(direct_mtls, tomasz.walczuk)` for a dedicated direct-client certificate. These are distinct controller namespaces: a direct client cannot take over a queued session or vice versa. Selected SSH identity name: `runner-mac-dispatcher`, held at the Mac `secrets/dispatcher_ed25519` path and to be authorized for `ubuntu` only with the fixed bridge command, no PTY/shell/forwarding. The dedicated pin file uses the verified development host key (ED25519 fingerprint `SHA256:ezxpJBu2U3XNiWVkm+G4FX4Hx7lyQpnOAaidHZl4CQM`); host-key rotation must fail closed until repinned. Selected mTLS direct-client identity name: `runner-tomasz-direct`; selected server identity name: `runner-linux-dev`, with SAN `IP:129.151.232.40`. The PoC CA private key is owned by `tomasz.walczuk` and is not placed on Linux or in Git; only its public trust certificate is installed there. Identity material has been provisioned, but the dedicated SSH public key is **not yet authorized** for its forced bridge command, and Runner's client-certificate principal map is **not yet deployed**; those are implementation/deployment gates, not assumed preflight passes.

## Remaining deployment gates and handoff

- The design and plan are aligned in commit `a54bcdc`. The selected endpoint is the **public** `129.151.232.40:8443`; the Linux bind is `10.0.0.200:8443`. The probe establishes basic ingress/bind/TLS transport only; `P106`/`P117` must establish the actual Runner listener, certificate-to-principal mapping, and authorized/unauthorized API behavior before claiming direct API readiness.
- Go and account-path prerequisites have been checked, but no plan can guarantee future host-capacity and software tests will never find a defect; a failed named gate still stops the sequence.
- The dedicated dispatcher key and host pin exist, but the key must be authorized only with the fixed SSH bridge command and mapped server-side to `(queued_mac, tomasz.walczuk)` in `P-NET-01`. The current `~/.ssh/remote-session-runner` key is a development-login key, not bridge evidence.
- The direct-client certificate exists, but `runnerd` must map its verified identity to `(direct_mtls, tomasz.walczuk)` and pass the later host gate. Do not commit private key material or treat a TLS handshake as authorization proof.
- The host is not disposable for physical power cuts. `P143` must report physical power-loss survival as unverified unless representative physical tests become available, and the plan requires explicit user approval before continuing on the software-crash-only path. A failed durability test cannot be waived.
- Commit this decision note in its own non-phase commit. `P001` then begins from a clean worktree, records that commit hash, and freshly reloads the entire current plan and both designs. Preflight decisions do not count as a PASS for later implementation gates.
