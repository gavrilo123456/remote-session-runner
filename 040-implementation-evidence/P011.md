## Scope and implementation choices

The P011 plan row is: SQLite open/migration scaffolding on both authorities with WAL, foreign keys, bounded busy timeout, sync, and owner modes. Its focused gate is the D-14 migration subset with prior-schema reopen. The detailed design specifies WAL, foreign keys, bounded `busy_timeout`, and proposed `synchronous=FULL`; migrations are applied before readiness and timestamps are UTC.

Implementation choices for this scaffold:

- Use `modernc.org/sqlite` v1.59.0 with `database/sql`, pinned in `go.mod`; it supports the selected Go version and both host architectures without CGO.
- Apply and verify `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000` (5 seconds), and `synchronous=FULL` for every pooled connection. The timeout is a fixed bounded opener default; config does not currently define a per-host SQLite timeout.
- Require an absolute, clean database path. Create the database parent directory owner-only and a new database file mode 0600; reject symlinks, wrong ownership, or group/other access on existing database paths. Verify database sidecar modes while active.
- Start the migration ledger at schema version 1. P011 creates only the migration ledger; authority/session tables begin in their assigned later phases. The prior-schema fixture will model a version-0 SQLite file with retained fixture data and constraints, then verify migration, WAL reopen, and data preservation.

These choices do not claim physical power-loss survival. `synchronous=FULL` configures SQLite behavior; only P143 can establish the named storage claim. If representative physical power-cut tests are unavailable, the software-crash-only path still requires my explicit approval.

## Implementation and test results

P011 adds `src/internal/store/sqlite.go`, `migrations/0001_schema_migrations.sql`, and `sqlite_test.go`; it replaces the placeholder `store/doc.go` and pins `modernc.org/sqlite` v1.59.0. `store.Open` requires an absolute clean path, creates an owner-only parent and mode-0600 database, rejects symlinks and unsafe existing modes, and finishes SQLite initialization/migration before returning. It verifies WAL, foreign keys, a 5-second busy timeout, and `synchronous=FULL`; the connection DSN reapplies the per-connection settings for every pooled connection. Schema v1 adds the migration-history ledger, applies each version in an immediate transaction, records a UTC timestamp and SQL checksum, checks history against `PRAGMA user_version`, and refuses a future or inconsistent schema. P011 adds no authority/session tables; those are later-phase deliverables.

An early focused run found that setting `journal_mode=WAL` as a per-connection DSN pragma let simultaneous openers contend and one failed with `database is locked (SQLITE_BUSY)`. WAL is now established once during startup with bounded busy retry; the journal mode persists for the database, while foreign keys, timeout, and synchronous mode remain configured on every pooled connection.
