## Bounded P152 contract

1. Persist `mailbox_id`, the client-visible request ID, and a deterministic
   internal exchange ID for every mailbox exchange. Existing retained rows
   migrate to `mailbox_id: default`; existing filesystem projections remain in
   the default root.
2. Use the internal exchange ID for foreign keys and cleanup records. Scope
   receipt lookup, idempotency lookup, response publication and recovery, ACK,
   event-file references, and cleanup by mailbox identity.
3. Preserve raw client request IDs and idempotency keys in mailbox JSON and
   responses, but derive an internal bounded execution idempotency key before
   a mailbox mutation reaches local intents, jobs, commands, or remote bridge
   frames. Existing retained rows retain their existing execution key so
   recovery cannot retarget or replay historical work.
4. Keep the current single runtime explicitly bound to `default`. P153 owns
   default/override resolution; P154 owns composition of multiple runtimes.

## Implementation and review

Schema migration 25 replaces the global mailbox receipt identity with a
deterministic, versioned internal exchange ID derived from the mailbox ID and
the client request ID. It retains the client-visible request ID and raw client
idempotency key, while new mailbox mutations receive a separate opaque
execution idempotency key before entering local intents, jobs, commands, or
queued remote frames. The internal ID is now the foreign key for mailbox event
references; cleanup ownership for event artifacts is `(mailbox_id, command_id)`.

The migration moves every retained v24 exchange and its response, ACK,
reference, and cleanup state to `default`. It preserves historical execution
keys exactly, so a retained pre-P152 request keeps its original recovery
identity. New reads and writes select their mailbox scope explicitly. The
former unscoped store methods remain compatibility wrappers for `default` only.

The current `runner-local` composition explicitly instantiates its importer,
session processor, ACK importer, and artifact cleaner with mailbox ID
`default`. It does not compose the configured multiple roots; P154 still owns
that production wiring. Mailbox JSON cannot provide a mailbox ID or execution
key. The configured importer stamps the trusted mailbox ID, and the session
processor copies the durable execution key into a request only after receipt
acceptance.

The final review found and fixed two test-quality issues before the phase
gates: P102 now names its mailbox-scoped execution behavior accurately, and
the v24 fixture asserts all retained parent fields rather than only a subset.
No implementation blocker remained.
