## Predeclared P142 workload and acceptance statistic

- On each host, the test creates 20 isolated persistent-shell sessions and starts exactly four concurrent commands, one per session, while the other 16 remain ready. It checks 20 session reservations and four live command slots throughout a ten-minute measured interval. A health sample every 30 seconds checks session/command states and durable slot counts.
- Each active command emits 6,000 newline-terminated 4,096-byte records at 100 ms intervals (10 records/second for ten minutes). The 24,000 measured records are approximately 96 MiB of persisted output total; each command stays well below the 100 MiB per-command cap. Each record carries a `time.time_ns()` timestamp immediately before its `os.write`.
- The primary visibility metric is per-host p99 elapsed time from that producer timestamp to a completed `ReplayCommandEvents` read that returns the same committed event payload and sequence. This includes runtime output draining, 50 ms chunking, SQLite persistence, subscriber delivery, and the independent durable read. The test reports p50, p95, p99, maximum, sample count, and count above 500 ms. **Acceptance is p99 <= 500 ms on each host separately**; a pooled cross-host percentile cannot hide a host miss. A failed p99 gate blocks P142 PASS.
- On one measured command, a separate unread subscriber remains unread while a 1,310,720-byte startup burst is persisted. Its queued payload high-water must stay at or below the configured 1,048,576-byte limit and it must report `ErrSubscriberOverflow`; the retained cursor must replay contiguously through the terminal event after the ten-minute command completes. Burst bytes are excluded from the latency statistic.
- Each of the four normal subscribers consumes and acknowledges events; its observed byte high-water must not exceed 1 MiB. Every measured marker must appear exactly once in the durable event sequence. All four commands must succeed with complete, untruncated output; all 20 sessions and four slots must remain stable during the measured interval. The test records process RSS/available memory with the existing P141 host sampler at a one-second interval and requires peak fixture RSS to fit within its pre-test available-memory reading.
- Each host test has an 18-minute Go test timeout, allowing setup, ten minutes of load, and confirmed cleanup. Cleanup must confirm stop of every fixture runtime and leave zero ownership markers and zero durable session/command reservations.
