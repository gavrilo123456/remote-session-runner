## Implementation

P154 replaces the singleton Mac mailbox composition with an ordered runtime per
configured inbox. Each runtime has its own importer, session processor, ACK
importer, event projection, and artifact cleaner. The Mac authority, local API,
local Router driver, remote Router driver, and health monitor remain shared.
One failed mailbox cycle records a bounded operational error and does not skip
the remaining configured roots.

Version 1 continues to synthesize the existing `default` root. The new
`deploy/macos/mac.v2.yaml.example` shows a named-inbox configuration while
retaining only the current `linux-host`; it adds no second host. Health metrics
now include bounded backlog counts per configured inbox as well as the existing
total.

The installer accepts an owner-only staged config inside the selected config
directory. It validates the candidate while the current service remains live,
quiesces `runner-local` then `runner-locald`, waits for their sockets to go
away, and performs a final read-only retained-state check. The irreversible
candidate boundary then records every candidate mailbox root in migration 27's
append-only registry before `mac.yaml` is handed off. This prevents a later
version-1 rollback from silently abandoning a marker-last request published to
a new root after activation. A pre-boundary failure restores the prior
LaunchAgents. A post-boundary failure keeps the active candidate or retains the
exact staged candidate path and prints its rerun command.

Migration 27 is deliberately not seeded with a Mac-specific path because the
shared SQLite schema also runs on Ubuntu. Read-only validation uses the literal
legacy default as a baseline for P153-era databases until the Mac activation
boundary records it. A registered inbox ID/root is append-only in this PoC;
removal, rename, or relocation needs a later explicit migration procedure.

## Focused proof and review

- The two-inbox runtime fixture processes equal client request IDs and
  idempotency keys independently, publishes per-root responses/events, accepts
  per-root ACKs, and cleans only the matching artifacts.
- The retained-work fixture proves a request accepted after an early candidate
  check causes the final removed-inbox check to reject installation.
- The activation regression records a candidate root, creates a marker-last
  request without importing it, and proves both in-process and read-only
  version-1 removal checks reject the rollback.
- The failed-candidate regression proves a construction failure before an
  installer activation boundary leaves a version-1/default runtime able to
  start and register its root.
- Security fixtures reject symlinked ancestors and non-`0700` mailbox roots;
  all configured root components are owned by the current user and mode `0700`.
- The installer/config fixture checks static validation, ordered quiescence,
  final retained validation, candidate registration before config handoff,
  pre-handoff recovery preservation, and bootstrapping order.
- Final independent code review passed with no remaining reproducible P154
  correctness, security, multi-inbox, metrics, or v1 compatibility blocker.
