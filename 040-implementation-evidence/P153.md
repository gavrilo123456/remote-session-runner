## Frozen implementation decisions

1. `environment` and `execution_target` are treated as an atomic pair for
   mailbox `run` and `create_session`: both omitted means the trusted inbox
   default; both present must match exactly one context in that inbox's
   allow-list; either one alone is rejected before a local intent or route is
   created.
2. `repository_alias` is an optional, bounded field only for those two
   new-work operations. When supplied, it must be one of the inbox's configured
   aliases. It is policy/audit metadata only: it never supplies a path, creates
   a checkout, changes source mode, or selects a host.
3. The durable mailbox exchange stores the resolved context/environment/target,
   selection source, selected alias, and configured alias scope. Retained-key
   retries reuse that stored selection before canonicalization, so a later
   configuration-default change cannot retarget a retry or an existing session.
4. Responses add `inbox_id` for processor-produced exchanges. Successfully
   selected `run` and `create_session` responses also add the selection source,
   resolved environment, and resolved target. The response schema keeps these
   additive fields optional so retained v25 terminal response bytes remain
   readable and immutable.
5. Safe selection metadata is appended to the allowed mailbox audit row in the
   same transaction as the local intent. Raw scripts, output, credentials,
   paths, and secret references remain excluded from audit records.
6. A v25-to-v26 migration keeps legacy exchange and audit selection fields
   absent; it does not fabricate a current default for historical work.

## Implementation and review

The Mac configuration now resolves a mailbox new-work request into a trusted
immutable execution selection. Omitting both `environment` and
`execution_target` uses the configured inbox default. Supplying just one is
rejected. Supplying both requires the exact configured and inbox-allowed
context. An optional `repository_alias` must be inside the mailbox's bounded
alias scope and remains metadata only.

Mailbox request parsing preserves whether each member of the target pair was
present, while the v1 JSON schema permits the P153 omission only for
`create_session` and `run`. The processor resolves the selection before it
forms the durable receipt and passes only that stored selection to the Mac
local API. The local API therefore does not execute a raw mailbox target that
disagrees with the trusted selection, and it excludes the top-level alias from
the API execution body.

Migration 26 adds selection fields and a durable provenance state to mailbox
exchanges. Existing v25 rows remain selection-free and `legacy`; no current
default is invented for them. New resolved work is `resolved`; a policy
rejection is durably `rejected` before response publication. This closes the
selection-rejection crash window: a retry cannot become executable simply
because configuration later changes. A v25 accepted new-work row can resume
only for its original complete, still-allowed explicit pair. Retained-key
retries retain their original snapshot, including an explicit selection when a
later retry omits the pair.

Responses add optional `inbox_id`, `execution_selection_source`,
`resolved_environment`, and `resolved_execution_target` for processor-created
work. Allowed mailbox create/run audit rows receive only bounded selection
metadata in the same transaction as local-intent acceptance. Scripts, output,
paths, credentials, and secret references are not added to audit data.

Final review identified and closed these boundary cases before the phase
gates: a resolver output must match the raw request form and mailbox ID; a
rejected selection stays terminal across both crash recovery and same-key
retry after a configuration change; a retained explicit selection is reused
when its retry omits the target pair; and the test migration now proves
terminal receipt, ACK, event reference/cleanup, audit append-only behavior,
and foreign-key integrity.
