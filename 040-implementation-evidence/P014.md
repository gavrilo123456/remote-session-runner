## P014 deliverable

Add the next SQLite migration and authority-store API/tests for command acceptance:

1. `exec_commands` stores the stable command ID, parent session, authoritative ordinal, optional source intent ordinal, canonical request hash, exact immutable script bytes, script SHA-256, queued state, timestamps, and later terminal bookkeeping fields. The parent session foreign key and `(session_id, ordinal)` uniqueness are enforced by SQLite.
2. `exec_command_events` stores `(command_id, sequence)` with event type, payload/byte count, and timestamp. The acceptance row is exactly sequence 1 with type `command_queued`.
3. `AcceptCommand` validates the parent session and queued command input, rejects invalid UTF-8 or scripts above the 128-KiB decoded-byte limit before any insert, allocates the next authoritative ordinal under the write transaction, and inserts command plus sequence-1 event atomically. No scheduler, runtime, or process starts in this phase.
4. Reads validate stored script bytes against the stored SHA-256 and UTF-8/size contract so a corrupt script is rejected rather than returned as executable data. Reopening the WAL database must preserve exact script bytes, hash, command state, ordinal, and event.

P015 owns the reusable mutation idempotency lookup/conflict API; P016 owns the stronger contiguous-order/eligibility rules; P017 owns general event append/replay and terminal bookkeeping. P014 may allocate the initial ordinal needed by its transaction but does not claim those later gates.
