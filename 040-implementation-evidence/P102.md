## Implementation and test approach

P102 is a contract-matrix phase. `src/internal/localapi/p102_test.go` reuses the real Unix-socket HTTP harness and the file-only mailbox processor. For each operation, it accepts through Unix first and mailbox first, replays the canonical-equivalent operation across both ingresses with the same idempotency key and a fresh mailbox request ID, then varies behavior under the same key through both ingresses and checks the conflict. It asserts stable resource/intent identities and one durable operation binding. The run case completes a local one-off job and checks one start event and one job/session/command; the close case records one closing and one closed transition after retries. No production defect was exposed, so this phase changes tests and evidence only.

Planned gates on the Mac source checkout, pinned Go 1.27.1:

1. Focused P102 local API tests, followed by the P096/P098/P100/P101 adjacent contract tests.
2. Full hermetic `make test`.
3. `make vet`, `make build`, and `make smoke`.
4. D-12/P005 import-boundary checks, Go formatting, and `git diff --check`.
5. Review the full staged diff and exact assertions before a single P102-scoped implementation commit.
6. Push to GitHub `dev`, fast-forward the clean Ubuntu `dev` checkout, verify equal commit IDs, and run the synchronized Ubuntu `localapi`, `mailbox`, and `store` package tests before evidence closeout or P103.

No live Runner-process or direct HTTPS application test is assigned to P102. The test harness is hermetic and does not use remote credentials, call the CLI as a mailbox client, or claim Linux worker execution. P143's physical power-loss/software-crash approval gate remains unchanged and is not treated as satisfied.
