## Planned deliverable and gates

1. Add a bridge `RequestHandler` implementation that translates only `create_or_resume_session` and `get_session` into the existing private `runnerd` HTTP routes; the handler performs no shell, runtime, SQLite, or scheduler work.
2. Build create payloads with stable frame `resource_id`, `idempotency_key`, request ID, and the server-mapped controller. Build read requests with controller query parameters derived from that same server-side mapping.
3. Use an injected HTTP client and a Unix-socket client constructor, bound response limits, strict JSON object responses, and status-to-protocol error mapping. A repeated create frame sends the same stable mutation to exercise safe retry/idempotency; no replacement ID is allocated.
4. Add fake HTTP request/reply/retry/error fixtures and an Ubuntu real-host bridge-to-private-runnerd session gate using the Linux runtime adapter.
5. Run P050 focused tests, the full Mac hermetic/vet/build/smoke/race/format/diff gates, then synchronize and run the named Ubuntu host suite.

## Unresolved assumptions

- The bridge's `resource_id` is the stable private runnerd `session_id`; the frame's `request_id` is forwarded only as an exchange correlation field and is excluded from mutation identity by runnerd's canonical hash as designed.
- `get_session` uses the private API's `controller_type` and `controller_id` query parameters because that endpoint has no mutation body. These values are always generated from the authenticated key mapping, never from frame payload.
- P050 forwards only session create/read. Command, job, cancel/close, and event forwarding remain later P051–P054 deliverables.

## Implementation results

**Status: PASS**

- Added `src/internal/sshbridge/forward.go` with `RunnerdForwarder`, an injected HTTP/JSON adapter for P050 session create/read operations and a Unix-socket HTTP client constructor for the owner-only `runnerd` socket.
- `create_or_resume_session` maps the stable frame `resource_id` to the private `session_id`, forwards the same idempotency key/request ID and immutable session payload, and derives the private controller object only from the authenticated server-side mapping. Repeating the frame sends the same stable request body; no replacement ID is allocated.
- `get_session` derives `controller_type`/`controller_id` query parameters from the mapped controller and never accepts controller fields from the bridge payload.
- Responses are bounded to the shared one-MiB ceiling and must be JSON objects. Private HTTP statuses map to protocol error codes; dial/transport failure is reported as retryable `transport_uncertain`. No shell, runtime, SQLite, scheduler, SSH process, or second execution path was added.
- Added fake HTTP request/reply/retry/error fixtures and an owner-only Unix-socket forwarding fixture. Command, job, cancel/close, and event operations remain later P051–P054 work.
