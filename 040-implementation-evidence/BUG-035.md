## Observations and limits

At the first bounded sample, the same-incarnation unsuffixed PRD `runnerd`
consumed 2.32 CPU seconds over about 5.70 wall seconds, **40.72% of one CPU**.
Dev and QAS each measured about **0.18%**. Aggregate hypervisor CPU steal was
**91.36%**; this is distinct from the Runner process's CPU consumption.

Diagnostic counts found 314 terminal PRD sessions: 313 closed and one lost;
no nonterminal sessions. Dev had 17 closed sessions and QAS 16. PRD retained
one session reservation and one command slot for the original LOST GPU
request. These diagnostic counts are not a supported complete recovery
inventory, process-exit proof or authority to release that capacity.

After the failed source-test group was separately stopped, the
**20:34:53.603881 UTC** sample still measured the same PRD incarnation at
**32.94% of one CPU** over 5.10 seconds, versus **0.196%** each for Dev/QAS.
Steal was **92.73%**. Thus the earlier source-test process is not required for
the observed PRD activity. No claim of an exact hot function follows from this
sample. No built-in CPU profiling endpoint was found, the host reports
`perf_event_paranoid=4`, and no live profiler was attached.

Source inspection identifies a concrete avoidable cost: the once-per-second
policy loop previously called `ListSessions`, fetched every historical ID,
decoded each full row and only then skipped terminal states. An overloaded
sweep may keep a tick pending and run again immediately. Incoming status reads
and periodic metrics are additional possible CPU contributors; their exact
shares were not measured. The relevant worker code is unchanged between the
observed installed release and the investigation source.
