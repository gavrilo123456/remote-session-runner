# HTTP/JSON v1 contract

`openapi.json` freezes the public Direct API at `https://129.151.232.40:8443` and requires TLS 1.3 mutual TLS with an explicitly mapped client certificate. The host-local listener binds to `10.0.0.200:8443`; that bind address is deployment configuration, not a client URL.

The same path and JSON contract is available through the owner-only Mac Unix socket at `/Users/tomasz.walczuk/Library/Application Support/RemoteSessionRunner/run/local-api.sock`. The `x-runner-local-unix-socket` OpenAPI extension records that ingress because OpenAPI's HTTP TLS security schemes cannot represent kernel-authenticated Unix sockets. The local socket uses the `tomasz.walczuk` OS account and `(local_user, tomasz.walczuk)` controller; it does not require or claim HTTP mTLS. Local mutation responses have `acceptance_scope: local_intent`. Direct HTTPS operations require mTLS and use the mapped `(direct_mtls, tomasz.walczuk)` controller; direct create and one-off job accept only `remote` targets, and target-authority acceptance has `acceptance_scope: target_authority`.

The account mapping remains `local` → `tomasz.walczuk` and `remote` → `ubuntu`. Create-session and one-off-job requests name `execution_target`; command requests contain no target field and inherit the session's immutable target. The 202 acceptance envelopes carry both `resource_id` and the resource-specific stable ID; those values are equal. A local queued remote acceptance reports `known_state.delivery_state: recorded` and omits target-authoritative session/command state until Linux confirms acceptance. The `mac-dev` and `linux-dev` environment names in the contract fixtures are examples only; they do not configure or pass the later runtime registry gate.

Read snapshots are wrapped in `{view, is_stale, resource}`. `view` is `authority`, `projection`, or `local_intent`; the resource's `observed_at` is the snapshot time. A retained local intent that was never delivered reports `delivery_state: not_delivered` and its stable IDs without inventing session, command, job, or teardown state. Event NDJSON responses use `X-Runner-View` and `X-Runner-Stale` headers. `GET /v1/commands/{command_id}/events` returns `410` with `event_history_unavailable` and `details.output_complete: false` when the requested range has expired or is irrecoverably gapped. Each line in a successful stream is one P002 command-event object.

The selected v1 job status fields are `phase` (`creating_session`, `accepting_command`, `awaiting_command`, `closing_session`, `complete`, `failed`, or `lost`) and `teardown_state` (`pending`, `closed`, `failed`, `lost`, or `not_created`). A job snapshot includes stable job/session/command IDs, command state and exit/output result when known, target/controller/environment/source/capabilities, observation time, and view staleness. A local intent view contains delivery status and the same stable IDs, but no fabricated authoritative job phase or teardown result.

Mutation requests carry `Idempotency-Key`. Scripts are UTF-8 strings limited to 131072 UTF-8 bytes; the OpenAPI extension states this byte limit because JSON Schema `maxLength` measures Unicode characters. The API body ceiling is 1048576 serialized bytes and must be enforced before creating an intent or authoritative resource. No response claims that command completion follows from a 202 acceptance.

The temporary TLS probe in pre-implementation evidence validated transport and credentials only; it was not a Runner API test. This contract does not claim that the Runner listener or application has been built or tested.
